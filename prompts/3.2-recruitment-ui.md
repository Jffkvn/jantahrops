# Prompt 3.2 — Recruitment UI, talent pool, shortlist pack

Self-contained. Paste AFTER 3.1 has landed and its tests pass — this builds on
the tables, endpoints, and data layer from 3.1.

---

```
TASK: Build the recruitment UI — vacancies workspace, an applications pipeline
per vacancy, candidate profiles, interview tracking, a searchable talent pool,
and a client-facing shortlist pack. Uses the 3.1 data layer; do not re-implement
the schema or the endpoints.

Read this whole block first. Reuse the design system and the patterns from the
leads and finance features (board, detail sheet, timeline, server-side lists).


=== 0. WHAT ALREADY EXISTS — build on this ===

From 3.1: vacancies, candidates, applications, interviews, candidate_files
tables; enums vacancy_status, employment_type, application_stage,
availability_status; the public-jobs + public-candidates Edge Functions; the
`candidates` private bucket; recruitment-api.ts (createVacancy, publishVacancy,
closeVacancy, listVacancies, getVacancy, listCandidates, getCandidate,
updateCandidate, cvSignedUrl, listApplications, moveStage, addApplicationNote,
createApplication, scheduleInterview, recordInterviewFeedback);
candidate_waiting signal in the Day View.

Design system + shared pieces already in the repo (reuse — do NOT rebuild):
- Components: Button (primary|secondary|ghost|highlight|danger|link),
  Input, Textarea, Select, Checkbox, Switch, Label, Badge, Card, Dialog, Sheet,
  DropdownMenu, Tooltip, Tabs, Table, Skeleton, Toast (sonner), Separator,
  Avatar, Popover, ScrollArea, StatusChip (success|warning|danger|info|neutral),
  PageHeader, EmptyState, PageSkeleton, Money, DataTable, Logo.
- Patterns to copy: the leads Kanban board (drag-to-move stages) →
  applications board; the lead detail sheet (header + facts + stage control +
  timeline + note composer) → candidate/application detail; the leads
  server-side table + filters; the ⌘K deep-link pattern (?param consumed once).
- lib: formatUGX/formatUGXCompact/parseUGX, formatDate/formatRelative,
  toDateInputValue/dateInputToISO (Africa/Kampala), getSupabase,
  normalizeUgandanPhone, cn.
- Tokens only for colour (bg-surface, text-ink, bg-primary, text-primary-ink,
  bg-highlight, StatusChip variants, etc.). rounded-card/control/pill,
  font-display/body, shadow-float (overlays only). No hex outside src/styles.
- Nav already has Recruitment (/recruitment) and Talent Pool (/talent) items on
  placeholder pages — replace them. React Query for server state.

Conventions: TS strict, no any; money bigint whole UGX; server-side paginated
lists; Row types stay `type` aliases; tests must be able to fail (paste RED),
never weaken an assertion.


=== 1. RECRUITMENT PAGE (/recruitment) — vacancies ===

Replace the placeholder.
- PageHeader "Recruitment", action "New vacancy" (opens the vacancy editor).
- A vacancies list (DataTable or cards): title, client organisation, location,
  employment type, status chip, applicant count, published state. Filter by
  status; search by title/organisation (server-side). Row → vacancy detail.
- Small counters: open vacancies, total active applicants.


=== 2. VACANCY EDITOR + DETAIL ===

Editor (create/edit): title (auto-slug from title, editable, must stay unique —
surface a clear error on collision), client organisation (search existing orgs),
summary, description, requirements, location, employment type, salary min/max
(UGX, bigint), closes date. Save as draft.
Publish control: "Publish to website" → publishVacancy (is_public=true,
status='open', published_at). A published vacancy shows a note: "Live on the
website job board." Pause / Close controls. A visible link to the public job
URL (the website job page) is optional.

Vacancy detail = the applications pipeline for that vacancy (§3), plus the
vacancy facts and a timeline.


=== 3. APPLICATIONS PIPELINE (per vacancy) ===

A Kanban board across the application stages — copy the leads board exactly
(drag-to-move, per-column counts, card click opens the candidate/application
detail). Columns:
  New, Screened, Shortlisted, Interview scheduled, Interviewed, Offered, Hired
  (Rejected and Talent pool are terminal — not board columns, but reachable from
  the detail's stage control and filterable in a table view.)
- A card shows the candidate name, headline, years experience, a rating dot if
  set, and the applied-relative date.
- Moving to 'rejected' requires a reason (like leads 'lost').
- Moving to 'hired' offers to mark the vacancy closed.
- A table view alternative with all stages + filters, server-side.


=== 4. CANDIDATE / APPLICATION DETAIL (sheet) ===

Header: candidate name, headline, contact quick-actions (call / WhatsApp /
email, from the contact — reuse the leads detail pattern). Application stage
chip.
Facts: years experience, skills (chips), salary expectation (Money), availability,
rating (editable 1–5), source, applied date.
CV: a "View CV" button that fetches a signed URL (cvSignedUrl) and opens it —
never a public link. Show "No CV on file" when absent. If cv_parsed is present
(AI, later) show the parsed summary; until then just the file.
Stage control: move the application through stages (writes the activity via the
3.1 trigger).
Interviews: list scheduled interviews; "Schedule interview" (date/time, mode,
panel, ) and, after, "Record feedback" (rating, outcome, notes).
Timeline: activities for subject_type='application' (and the candidate), reusing
the shared timeline component.
Note composer: adds a note activity.


=== 5. TALENT POOL (/talent) ===

Replace the placeholder. The searchable candidate asset — every candidate,
across all vacancies and self-registrations.
- Search box (server-side full-text over name / headline / skills — the 3.1
  listCandidates). Filters: skill chips (multi-select from distinct skills),
  availability, available-only toggle.
- Results: candidate cards/rows — name, headline, top skills, years, availability
  chip, rating, last-active. Row → the candidate detail sheet (same as §4 minus
  the application-specific bits, or the full sheet scoped to the candidate).
- "Add to a vacancy": from a candidate, create an application to an open vacancy
  (createApplication) — this is how you pull a pooled candidate into a pipeline.
- Empty state points at the public registration link + "add candidate manually".
- A manual "Add candidate" form (name, contact, headline, skills, CV upload to
  the private bucket) for candidates you meet offline.

Note: semantic ("who's done HR compliance in manufacturing") search is a
deferred AI feature — full-text is the search here for now. Do not build the
embedding call.


=== 6. SHORTLIST PACK (the client deliverable) ===

The thing a client actually sees. From a vacancy, select shortlisted candidates
and produce a clean, branded, printable pack — the recruitment equivalent of the
finance print view.

- From the vacancy, a "Shortlist pack" action gathers the applications in the
  'shortlisted' stage (or a manual selection).
- A print route /recruitment/:vacancyId/shortlist (rendered WITHOUT the app
  shell, @media print, black-on-white, A4) showing: the JantaHR letterhead (from
  company_profile), the vacancy title + client, then one section per candidate —
  name, headline, years, key skills, a short profile (from notes / parsed CV
  when available), salary expectation, availability. DO NOT expose internal
  ratings or private notes not meant for the client — include only
  client-appropriate fields. "Print / Save as PDF" button.
- (Sharing a live link is a later enhancement; the print/PDF is the deliverable
  now.)


=== 7. ⌘K + Day View touches ===

- Extend the ⌘K command bar search to also find candidates (name/headline) and
  vacancies (title), opening the relevant detail — same flat-list pattern as
  the existing lead search.
- The candidate_waiting signals from 3.1 already surface on the Day View; make
  sure clicking one opens the application detail (wire the subject_type='
  application' → open handler), mirroring how lead signals open the lead.


=== 8. TESTS ===

Component/logic (light — heavy correctness is in 3.1):
- The applications board groups by stage correctly and a drag calls moveStage.
- The talent-pool search calls listCandidates with the typed term (debounced).
- The shortlist print route renders the vacancy title, each selected candidate's
  name + skills, and does NOT render internal rating / private notes.
- Slug generation from a title produces a valid unique-able slug; a collision
  surfaces an error (mock the api).

Do not over-test UI. No snapshot tests. Reuse the RLS coverage from 3.1 for
data-layer correctness.

Testing rules unchanged: never weaken an assertion; break each new test to
confirm RED then restore; no float in a money test.


=== 9. ACCEPTANCE ===

  npm run check
  npm run build
  npm run dev
    # /recruitment: create a vacancy, publish it, confirm public-jobs returns it.
    # Register a candidate via the public-candidates endpoint (curl) → it appears
    #   in the talent pool and (if a vacancy slug was given) in that pipeline.
    # Move an application through stages; schedule an interview; record feedback.
    # Build a shortlist pack and open its print preview.

Report:
  1. Files created/changed.
  2. Screenshots: the vacancy applications board, the candidate detail sheet
     (with View CV), the talent pool with a skill filter, and the shortlist pack
     print preview.
  3. Confirmation the shortlist pack excludes internal rating/private notes and
     that CVs open via signed URL only.
  4. Confirmation no hex outside src/styles and Row types stayed `type` aliases.

Then stop.
```

      with a vacancy slug, in that pipeline

      trigger) and a `candidate_waiting` signal clears when you move a stale one
- [ ] Shortlist pack: branded, black-on-white, **no internal rating or private
      notes** — only client-appropriate fields
- [ ] CVs open only via signed URL; the bucket stays private
- [ ] Semantic search is NOT built (deferred); full-text search works
